# CareLink Follow-Up — Resilience, Offline Operation and Data Integrity

## D1. Duplicate Submissions and Idempotency

### 1. Making replayed operations safe

The API should treat every client-generated write as an operation, rather than assuming that every HTTP request represents a new operation.

Every mutation generated by a client receives a globally unique `operation_id`, for example a UUID:

```text
operation_id = 7d4c3c8e-...
device_id    = FAC-0101-TABLET-03
user_id      = clinician-123
operation    = CREATE_VISIT
```

The client sends this identifier with every retry.

The server maintains an idempotency record containing at least:

```text
operation_id
device_id
authenticated_user
operation_type
request_hash
status
result/reference
created_at
```

The idempotency record and the business mutation must be committed in the same database transaction, so the server cannot record an operation as processed while failing to persist the corresponding clinical change.

The server enforces uniqueness on the operation identity.

For example:

```text
(device_id, operation_id) is unique
```

or a globally unique operation ID is enforced directly, depending on the chosen identifier scheme.

If the same operation is received again, the server does not create another visit. It returns the result of the original operation.

#### Example

The client submits:

```text
Operation A
CREATE_VISIT
operation_id = ABC123
```

The server creates Visit `987` but the response times out.

The client cannot know whether the server received it, so it retries:

```text
Operation A
CREATE_VISIT
operation_id = ABC123
```

The server sees that `ABC123` has already been processed and returns:

```text
already_processed
visit_id = 987
```

No second visit is created.

This is important because a timeout is an unknown outcome, not proof that the operation failed.

The same mechanism applies to patient creation, contact attempts and other retriable writes.

For operations where a natural business identifier exists, I would use that as an additional integrity constraint where appropriate. For example, patient identifiers should be unique within their facility according to the agreed patient identity model.

### 2. What the client must do

The client must persist the operation before attempting to send it.

A local outbox record should contain:

```text
operation_id
device_id
user_id
entity_type
entity_id/local_id
operation_type
payload
created_at
sequence_number
status
attempt_count
last_attempt_at
```

The client must never generate a new operation ID simply because a request timed out.

Instead:

1. Create the operation ID.
2. Persist the operation locally.
3. Apply the change locally if the workflow supports optimistic/offline operation.
4. Put the operation in the outbox.
5. Send it.
6. If the response is successful, mark it acknowledged.
7. If the request times out, retain the same operation ID.
8. Retry the same operation.
9. Remove/archive the operation only after the server acknowledges it.

This means the client can safely replay the queue after a crash, restart or network interruption.

### 3. How long idempotency state is retained

The server must retain idempotency records for at least as long as an operation could realistically be replayed by an offline device.

For this environment I would initially retain them for 90 days after successful processing, with the period configurable by operational policy.

The 90-day period should be longer than the expected maximum offline period plus reasonable device recovery/retry time.

The retention period should be longer than the maximum supported offline/replay window, with monitoring and an explicit quarantine path for devices that exceed that window.

The client should also retain acknowledged operation metadata locally until it has confirmed synchronisation and completed its local cleanup policy.

After the server's idempotency retention period expires, the system must not assume that an old operation ID will still be recognised.

Therefore:

- the API should reject or quarantine operations whose client state is too old to safely replay;
- the client should perform a controlled resynchronisation rather than blindly replaying ancient operations;
- operational monitoring should identify devices that have been offline beyond the supported window.

I would not silently accept an old operation and risk creating a duplicate.

### 4. Handling duplicates already in the database

Existing duplicates are a clinical data-quality problem, not simply a database-cleanup problem.

I would not run a script that blindly deletes duplicate patients.

#### Step 1 — Detect candidates

Use deterministic and probabilistic matching signals such as:

- facility;
- patient number;
- national identifier where legitimately available;
- name;
- date of birth;
- sex;
- phone number;
- historical visits.

The system should distinguish:

```text
Confirmed duplicate
Possible duplicate
Probably different patients
```

#### Step 2 — Preserve both records

Both records remain available while the duplicate is being reviewed.

The system records:

```text
duplicate_candidate
record_a
record_b
reason
detected_at
review_status
reviewed_by
reviewed_at
```

#### Step 3 — Clinical/records review

A suitably authorised records or clinical user determines whether the records actually represent the same person.

This is important because two patients can legitimately have similar names and dates of birth.

#### Step 4 — Controlled merge

If confirmed as the same patient, the system creates a canonical patient record and links the duplicate record to it.

Historical visits and other clinical information are preserved and re-associated through an auditable merge process.

I would not physically delete the source record as the first action.

The system should maintain:

```text
duplicate_patient_id
canonical_patient_id
merged_by
merged_at
reason
```

and an audit trail.

#### Step 5 — Prevent recurrence

After remediation, the identity rules and idempotency constraints should prevent the same class of duplicate from being created again.

Any automated merge capability should be limited to cases with extremely high confidence. Ambiguous clinical identities should always require human review.

## D2. Working Through an Outage

### 1. What the client caches

The offline client should use a local encrypted database rather than relying only on browser memory or temporary cache.

It should contain only the minimum information required for approved offline workflows.

For the Follow-Up module this could include:

- facility-assigned patients;
- patient number;
- name;
- relevant appointment/visit information;
- current follow-up status;
- phone number where clinically necessary;
- recent locally relevant clinical information;
- facility/reference data;
- pending local operations;
- synchronisation metadata.

The client should not download the entire national patient population.

The local cache should have a defined retention period. I would initially use:

- **active operational data:** retained while needed for offline operation;
- **stale data:** expired after a configurable period such as 30 days.

The 30-day figure is a local retention ceiling, not a freshness guarantee. The UI must show the last successful synchronisation time, and workflows requiring current information should be restricted when data exceeds the clinically acceptable freshness window.

- **completed/acknowledged outbox records:** retained locally only as long as required for reconciliation and audit support.

The exact retention period should be validated against Ministry clinical, legal and records-retention requirements.

A device that has been offline beyond the supported period should clearly show that some information may be stale and require synchronisation before higher-risk workflows are permitted.

### 2. Where the data is stored

The facility client should use an encrypted local database.

Depending on the supported device environment this could be an encrypted SQLite database or another OS-protected local store.

Encryption keys should be protected using the operating system's secure credential/key storage rather than being hard-coded into the application.

The local store should be tied to the device and application identity.

The national system remains the authoritative store once data has successfully synchronised.

### 3. Synchronising queued actions

When connectivity returns, the client synchronises the outbox rather than simply reloading the screen.

#### Ordering

Operations should have a local sequence number.

Operations affecting the same entity should be processed in their causal order.

For example:

```text
1. CREATE_VISIT
2. UPDATE_VISIT
3. RECORD_CONTACT
```

should not be reordered arbitrarily.

Independent operations can be processed concurrently where this is safe.

#### Retry

Transient failures such as:

- network timeout;
- connection reset;
- temporary server unavailability;
- HTTP `429`;
- temporary integration failure;

should be retried automatically.

Permanent errors such as:

- invalid payload;
- unauthorised operation;
- invalid patient;
- rejected business rule;

should not be retried indefinitely.

#### Back-off

Retries should use exponential back-off with jitter, for example:

```text
1st retry: ~2 seconds
2nd retry: ~4 seconds
3rd retry: ~8 seconds
4th retry: ~16 seconds
...
```

with a maximum delay.

This prevents thousands of offline facilities from reconnecting simultaneously and overwhelming the national API.

If the server returns `Retry-After`, the client should respect it.

#### Partial failure

A queue containing 100 operations:

```text
72 changes synchronised.
20 are waiting to retry.
8 require review.
```

The client must not roll back the 72 successful operations.

Instead:

```text
72 → ACKNOWLEDGED
20 → RETRY
8  → CONFLICT / USER ACTION
```

The sync cursor/outbox state is updated per operation.

The user should see something understandable, for example:

> 72 changes synchronised. 20 are waiting to retry. 8 require review.

No local work should disappear simply because another operation failed.

### 4. Monday Edit, Tuesday Central Change, Wednesday Reconnect

Consider:

```text
Monday:
Clinician edits patient record offline.

Tuesday:
The same record is changed centrally.

Wednesday:
Facility reconnects.
```

This is a conflict and should not be resolved using blind last-write-wins.

#### Step 1 — Client records the base version

When the clinician edited the record, the local operation includes the version of the central record that the clinician last knew about.

For example:

```text
base_version = 42
```

The central record is now:

```text
server_version = 43
```

#### Step 2 — Server detects the conflict

The server sees that the operation was based on version 42 but the current record is version 43.

It returns a conflict response such as:

```text
409 Conflict
```

with the relevant version information.

The server does not silently overwrite the newer central change.

#### Step 3 — User sees an understandable conflict

The clinician should see something like:

> This patient record changed while this device was offline.
>
> The central record contains newer information.
>
> Your offline change was saved locally but could not be applied automatically.
>
> **Review changes**

The UI should show enough information for an authorised user to understand what changed without exposing unnecessary information.

#### Step 4 — Who decides?

The system should decide automatically only for fields where the business rules make the merge unambiguous.

Append-only events should normally be merged automatically; competing clinical facts should be routed according to predefined clinical conflict rules.

For clinically significant conflicting fields, the authorised clinical/records user decides.

The merged record must retain provenance showing which source record each historical clinical event originated from.

The server remains the authority for the final stored record, but the business rule determines who is permitted to resolve the conflict.

The decision and both versions should be auditable.

For append-only events such as contact attempts, the preferred strategy is usually to retain both valid events rather than treat them as competing versions.

### 5. Protecting Sensitive Local Data

A shared clinic computer creates an additional security risk because multiple people may use the same physical device.

I would use several layers of protection.

#### Application controls

- Require authenticated CareLink users.
- Apply role and facility permissions locally as well as on the server.
- Lock the application after inactivity.
- Require re-authentication for sensitive actions.
- Never expose another facility's cached data.
- Clear sensitive data from application memory where practical.

#### Device controls

The Ministry should manage supported devices through appropriate endpoint/device-management controls.

This should include:

- full-disk encryption;
- operating-system accounts;
- automatic screen lock;
- security updates;
- malware protection;
- restricted local administrator access;
- remote wipe where supported.

#### Local database

The local database should be encrypted.

Encryption keys should be held by secure OS key storage rather than in the application bundle or source code.

Local backups should also be encrypted.

#### Offline session limits

Offline authentication should be time-limited.

A device should not be able to remain in an authenticated offline state indefinitely.

When connectivity returns, the application must revalidate:

- user account;
- role;
- facility assignment;
- device status;
- application version.

Client-side role checks are a usability control only; the national API remains the authoritative security boundary whenever connectivity is available.

### 6. Data I Would Refuse to Store Locally

The design should follow data minimisation.

I would not cache:

- the national patient population;
- patients belonging to other facilities;
- national administrative datasets;
- unnecessary historical clinical records;
- passwords;
- raw authentication credentials;
- access/refresh tokens in unprotected storage;
- database credentials;
- encryption keys alongside the encrypted database;
- unnecessary national identifiers where the offline workflow does not require them;
- laboratory data unrelated to the offline workflow.

If a piece of data is not required to keep an approved workflow functioning during an outage, the default decision should be not to cache it.

## 7. Resilience Principles

The resulting design follows five principles:

1. **Timeout does not mean failure.**  
   An operation may have reached the server even if the response was lost.

2. **Every retriable write has an operation identity.**  
   Replaying the same operation must be safe.

3. **Local work is durable before transmission.**  
   A connectivity failure must not destroy a clinician's work.

4. **Conflicts are explicit.**  
   The system must never silently overwrite newer clinical information.

5. **Clinical records are not disposable database rows.**  
   Duplicate remediation and merges require preservation, auditability and appropriate human review.

The objective is not merely to make the application "work offline". It is to ensure that when connectivity fails, the eventual return to the national system is safe, deterministic, auditable and clinically trustworthy.
